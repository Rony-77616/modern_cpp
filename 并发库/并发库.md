# 1.什么是并发库
c++并发库是标准库中用于处理多线程执行、共享数据、线程同步和线程通信的一组工具。可以分为四层：
  
任务执行层     thread、jthread、async
数据保护层     mutex、lock_guard、unique_lock
线程通信层     condition_variable
原子操作层     atomic






# 2.进程线程
进程和线程都是操作系统执行任务的单位，但是层次不同。
一个进程可以包含多个线程。

- 什么是进程？

进程是一个正在运行的程序实例。

例如打开两个记事本窗口，操作系统会创建两个进程：记事本进程A、记事本进程B。

每个进程通常有独立的内存空间、全局变量、堆、文件资源、系统资源，一个进程通常不能直接访问另一个进程的普通变量。

- 什么是线程？

线程是进程中的执行路径。一个进程可以只有一个线程，也可以有多个线程。例如进程下有主线程、下载线程、计算线程、日志线程等等。

同一个进程中的线程共享代码、全局变量、堆内存、打开的文件和资源。但每个线程有自己的栈、寄存器和程序执行位置


- 什么时候使用进程，什么时候使用线程？

适合使用线程：

 多个任务需要共享数据

 任务属于同一个程序
 
 需要较高通信效率
 
 计算、网络、文件操作可以同时进行

适合使用进程：
 
 任务需要严格隔离
 
 某个任务崩溃不能影响其他任务
 
 不同程序之间需要独立运行
 
 需要更强的安全边界





# 3.std::thread
- 创建线程
```cpp
#include<thread>
void work(){
    std::cout<<"thread working";
}

int main(){
    std::thread t(work);//可能从这里开始执行子线程，具体看操作系统调度
    std::cout<<"main thread working"<<std::endl;
    t.join();//join在这里让主线程等待t子线程执行完，再接着往下执行。

    return 0;
}
```

线程创建后就会根据操作系统的调度和主线程或者其他线程并行执行，直到join，等待它执行完后主线程再运行。join只负责等待结束。

主线程是操作系统创建程序时，创建的第一个线程，这个线程开始执行main，main是主线程的开始执行的入口。其余创建的线程都是子线程。

如果没有join，main结束时，t对象被销毁此时线程仍然是joinable状态，std::thread的析构函数会调用std::teiminate(),程序通常会异常终止。若调用了detach()，线程会和t对象分离，主程序不再等待他，风险是主程序结束后，子程序可能还没结束，或者要使用主程序已经销毁的变量时，会出错。


若线程传递参数要以引用的方式传递的话，必须要在传递时ref()显示引用传递，只靠函数里面的&传递不够，必须要两个都有。因为std::thread在存储参数时做的是：
1. 把参数拷贝一份到线程的内部存储
2. 调用存储的副本，副本是临时对象，不是主线程的对象。





# 4.std::mutex互斥锁
他解决的问题是，多个线程同时修改同一份数据时，如何保证数据不会被破坏。用于限制多个线程同时访问共享数据。

```cpp

#include<iostream>
#include<thread>

void add(int& count){
    count++;
}


int main(){
    int count = 0;
    std::thread t(add,count);
    std::thread t2(add,count);

    std::cout<<"主线程执行"<<std::endl;
    
    t.join();
    t2.join();
    return 0;
}

```
这段代码中，t和t2创建后，都是对count进行修改，而修改count的过程可以分为三步:
- 取count的旧值
- 算出++后的值
- 写回

在这期间，若t线程先运行第一步，在还没有运行第二部的时候，操作系统运行了t2线程，也是第一步，就会导致两次对同一个++取出相同的旧值，导致重复计算，也就是产生数据竞争，导致未定义行为，结果不能保证。


使用mutex后，让线程轮流修改
```cpp
mtx.lock();//
count++;
mtx.unlock();
```

std::mutex本身不保存对象，也不负责修改数据，他只负责控制同一时刻哪个线程可以进入被保护的代码。




mutex的状态:
```cpp
std::mutex mtx; //创建后 属于未上锁状态。

//直到某个线程执行：
mtx.lock(); //锁变为已加锁状态，并且这个线程拥有它
//若另一个线程执行mtx.lock()，就会暂停等待，直到第一个线程执行:

mtx.unlock();
```



mutex保护的是什么：

锁和数据之间没有自动绑定关系，例如mtx不会自动知道要保护count，如果某一段代码没有使用同一把锁，就没有被保护。
多个线程必须使用同一把锁。
```cpp
void add(){
    std::mutex mtx;
    mtx.lock();
    count++;
    mtx.lock();
}
```
错误。每次调用都有自己的锁，线程之间相互看不到对方的锁，所以不能保护共享的count。





解锁unlock：

执行完后必须要解锁，如果先return再unlock，就没有执行unlock，以后其他线程就不能执行这段代码，可能一直等待。


同一线程不能重复锁同一把普通mutex：
```CPP
mtx.lock();
mtx.lock();
```
普通的mtx不允许同一个线程重复获取同一把锁，二次lock()会导致一直等待第一次lock释放，但释放操作又无法执行，因此形成死锁。

同一个共享数据，所有相关线程必须使用同一把锁，而且锁的生命周期必须覆盖所有线程的使用时间。


# 5.std::lock_guard

让加锁和解锁自动完成。

之前的写法：
```cpp
mtx.lock();
count++;
mtx.unlock();
```

使用lock_guard后：
```cpp
{
std::lock_guard<std::mutex> guard(mtx);
count++;
} //离开作用域，自动解锁。
```


```cpp
std::lock_guard<std::mutex> guard(mtx);
```
这句代码可以拆分成三个部分：
1. std::lock_guard()<std::mutex>： 管理mutex的对象类型
2. guard: lock_guard类型的变量名，可以换成其他名字
3. mtx：guard要管理的那一把锁。


创建guard时会调用mtx.lock(),如果被其他线程持有，就等待。销毁guard时会调用mtx.unlock()。

特别注意：解锁位置由作用域决定。即使提前return，局部对象也会被销毁，因此会自动解锁。


mtx和std::lock_guard的关系：

mtx是真正的锁，而lock_guard是管理这把锁的对象。

两个线程可以各自创建一个guard，虽然guard1和guard2是不同对象，但是他们只要管理同一个mtx，因此可以用于保护对象。



# 6.unique_lock

和lock_guard一样管理mutex，但允许提前解锁、重新加锁，以及推迟加锁。

```cpp
std::mutex mtx;

{
    std::unique_lock<std::mutex> lock(mtx);
    //自动加锁

    //共享数据操作
}//如果仍然持有锁，就自动解锁。
```

最重要的是可以手动控制：
```cpp
std::unique_lock<std::mutex> lock(mtx);
count++;
lock.unlock();//提前手动解锁

//执行不需要共享数据的工作

lock.lock();//再次加锁

count++;

//注意：这些提前解锁再次加锁的操作应该通过std::unique_lock的对象lock来完成，而不是直接操作mtx，让他能够正确记录锁的状态。
```

如果已经调用了lock.unlock(),对象销毁时就不会重复解锁。

还可以在创建unique_lock对象时先不加锁：
```cpp
std::unique_lock<std::mutex> lock(mtx,std::defer_lock); //此时没有持有锁，可以先做准备工作

lock.lock();//到这里才真正加锁。
```
std::defer_lock的意思是“推迟加锁”。此时对象已经知道要加哪把锁，但还没获取它。


lock_guard和unique_lock的区别：
1. lock_guard只能在创建时自动加锁，离开作用域时自动解锁，而unique_lock支持手动加锁和解锁，也可以在创建时先不加锁。
2. 只需要保护一段作用域时，通常用lock_guard。需要调整持锁时间，用unique_guard。



# 7.std::condition_variable

std::condition_variable用来解决一个线程“暂时没有条件继续执行”的问题。例如：
- 消费者：队列没有数据，等待
- 生产者：放入数据，通知消费者
- 消费者：被唤醒，继续取数据

它本身不保存数据，也不判断业务条件。真正的条件通常由其他变量表示，condition_variable只负责让线程睡眠和唤醒。


基本组成：
```cpp
std::mutex mtx;
std::condition_variable cv;
bool ready = false;
```
三者职责不同：

mtx 保护ready，保证多个线程安全的访问ready
ready 表示条件是否满足，记录能不能继续执行，真正决定线程能否继续。
cv 让线程等待和通知，并在收到通知后重新检查ready，负责协调等待


下面给出一段代码：
```cpp
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <thread>

int main() {
    std::mutex mtx;
    std::condition_variable cv;
    bool ready = false;

    std::thread worker([&mtx, &cv, &ready] {
        std::unique_lock<std::mutex> lock(mtx);

        cv.wait(lock, [&ready] {
            return ready;
        });

        // wait 正常返回时，仍然持有 mtx
        lock.unlock();

        std::cout << "数据已准备好，开始工作\n";
    });

    {
        std::lock_guard<std::mutex> guard(mtx);
        ready = true;
    } // 释放 mtx

    cv.notify_one();

    worker.join();
}
```

这段代码的解析：
首先，这段代码是要实现让worker先等待主线程的notify信号后，再去实现worker线程的操作。
1. 首先定义一个互斥锁mtx，用来保护ready的修改，避免多个线程读它时发生数据竞争。定义一个cv，用来让线程等待和通知。定义一个bool类型的ready，用来控制此刻是否能执行该线程的工作。
2. 进入main主程序后，因为主线程和worker线程都创建了，二者谁先拿到mtx锁（两个线程都有创建容器获取锁mtx的操作）由操作系统调度决定，分为两种情况:
   - 情况一：主线程先拿到锁。

    此时，主线程先拿到锁（guard对象获取了mtx锁），他进行完数据获取后（代码中没有写出，实际工程中有可能是这样），将ready变为true，然后离开他的作用域，guard析构，将mtx解锁。然后调用cv的成员函数notify_one()，通知worker线程的wait检查ready。此时ready已经是true，就会调用wait判断成功，从而执行worker的打印操作。   
    
    注意1：wait需要等待的时候，会解锁mtx，并且执行等待。 wait条件判断成功的时候，不会解锁mtx，需要手动解锁，因此要unique_lock来获取mtx。

    注意2：若主线程先获取mtx，主程序执行到notify时，不能保证worker线程的打印操作和主线程的notify操作谁先执行。因为执行到notify时，worker线程并没有触发等待，worker也在执行，主线程前面一将mtx解锁，worker线程就可以立马获取mtx，同时此时ready也是true，wait判断不会等待，就直接进入打印操作了。因此还不需要主线程notify通知，worker就会直接执行了，只需要解锁并且修改了ready。而且子线程不是在等待状态的话，notify就不会通知他，只能由mtx解锁和ready来被动触发。

    流程图：

    |主线程|子线程|
    |:----|:----|
    |创建worker子线程|  |
    |获取mtx|    |
    |执行主线程操作|   |
    |修改ready=true|    |
    |解锁mtx|   |
    |notify子线程|     |
    |   |子线程获取mtx   |
    |   |检查ready，发现是true  |
    |   |wait直接返回，不进入等待|
    |   |解锁、打印、结束|




    - 情况三：worker子线程先拿到锁。
      此时，子线程先拿到锁。通过unique_lock拿到锁之后，此时ready还是初始化的false，执行到wait时，判断不通过，自动把传进来的mtx锁释放，然后开始等待。主线程此时就可以获取锁，然后按照上面的执行，由于已经开始等待了，所以直到notify，线程才能被唤醒，从wait等待，从wait被唤醒。然后通过wait传参在wait内部重新获取锁，再检查到true，继续往下执行。释放锁。


几个函数：
- wait(锁，判断lambda) : 是判断是否要等待的函数，return ready判断条件，若是true，就获取锁并且继续执行。若是false，就解锁，然后进入等待。接受一个锁的目的是万一要等待，把这个锁解锁。
- cv.notify_one():唤醒一个线程，唤醒之后，主线程继续执行
- cv.notify_all()：唤醒所有在这个cv上等待的线程，这些线程竞争mtx，不是直接执行任务。通知完后，主线程还会继续执行。


cv对象：

不同的cv对象，各自有独立的一组等待线程。

cv通常用于需要相互等待、通知的线程之间，不一定和主线程配合。要考虑两个问题：

1. 哪个线程需要等待，他调用cv的wait
2. 哪个线程能让条件满足？他修改状态，再调用notify。


ready要在锁内修改。原因是当主线程先拿到锁的情况下，假如将ready修改写在锁外，且已经将数据输入完了，然后解锁mtx，此时子线程可以接收到mtx，会开始执行。由于wait在判断和阻塞之间有一小段时间差（也就是需要时间），假如在这段时间之内主线程将ready修改为true了，而且notify也执行了，但是子线程还没有阻塞，没有同步。如果按正确的写法写在锁内，那么不论notify是否执行了，解锁后都可以wait判断成功，不会一直阻塞。所以，正确写法兼容两种顺序：状态先准备好，就直接通过；线程先等待，就通过通知唤醒。

还会产生数据竞争：解锁前完成的修改，对之后获取同一把锁的线程可见。如果不是一把锁，就不能保证。严格来说，普通变量存在数据竞争时属于未定义行为，因此不是“规定它可能读到旧值”，而是整个程序的行为失去标准保证。“读不到预期的 true”只是帮助理解的一种可能表现，不能据此断言某次运行一定会怎样。





# 8.std::atomic
之前在多个线程修改普通变量的时候需要加锁，但如果共享的数据只是一个简单的整数，可以用：
```cpp
#include<atomic>
std::atomic<int> count{0};
```
他表示count是一个支持原子操作的整数。多个线程执行count++时，每次加1都会作为一个不可分割的更新完成，不会出现两个线程的++相互覆盖。就不需要mutex每次保护count++了。

三个原子变量的最基本操作：
- 写入：count.store(10);
- 读取：count.load();
- 加一：count++；
- 还可以count.fetch_add(n);  加n后读取。

特别注意：变量是原子的，不代表他的表达式都是一次原子操作，例如：
```cpp
count.store(count.load()+1);
```
这里实际上是：原子读取 -> 计算加一 -> 原子写入。

读取和写入之间，其他线程仍然可以修改count，所以仍可能丢失加一的操作。因此计数器增加应该写++count或用fetch_add()。

atomic适用于单个计数器、简单状态等原子操作。
mutex适用于保护多步操作、多个相关变量、共享容器。
